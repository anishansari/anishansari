02What is an Activity?

Exercise Q1 of this unit asks: “What do you mean by android activity?” Let us build the answer step by step.

1 What is it?

An Activity is one screen of an Android app that the user can see and interact with. It is a Java class that extends Activity (or AppCompatActivity) and shows a layout file on the screen using setContentView().

Daraz has a Home screen, a Product screen, a Cart screen and a Checkout screen — each of these is usually a separate Activity.
2 What does it do?

An Activity holds the user interface of one task and handles the user’s actions on it: taps on buttons, typing in EditTexts, choosing from a Spinner. It also receives lifecycle callbacks from Android (onCreate, onStart, …) so it knows when it is created, shown, hidden or destroyed.

In the eSewa app, the “Send Money” Activity shows the amount box and the Pay button, and reacts when you press Pay.
3 Why needed?

Android needs a clear unit to put on the screen, to switch between, and to pause or close when something else happens. The Activity is that unit. Without a standard “screen object”, Android could not manage many apps sharing one small phone screen, memory and battery.

When a phone call arrives, Android knows exactly which screen (Activity) to pause.
4 When needed?

You need an Activity whenever your app has a screen. A one-screen calculator needs one Activity; a college registration app with Login, Form and Success screens may need three. The first Activity opened from the launcher icon is the one marked with the MAIN / LAUNCHER intent-filter in the Manifest.

5 What happens without it?

No Activity means nothing to show: the app has no visible screen and cannot take touch input. If you create an Activity class but forget to declare it in the Manifest, the app crashes when you try to open it (we will demo this later).

6 How it works?

Android creates an object of your Activity class, calls onCreate(), you call setContentView(R.layout.xxx) to inflate the XML, and the screen appears. From then on Android moves the Activity through its lifecycle states and calls the matching method each time the state changes.

03The Activity Life Cycle

“Every instance of Activity has a lifecycle. During this lifecycle, an activity transitions between three possible states: running, paused, and stopped.”

1 What is it?

The activity lifecycle is the set of states an Activity passes through from the moment it is created until it is destroyed, together with the callback methods Android calls at each change. The three main states in our notes are running (on screen and in focus), paused (partly visible / lost focus) and stopped (not visible).

Like a student in class: present and answering (running), present but distracted by a phone call (paused), gone home (stopped).
2 What does it do?

For each transition there is an Activity method that notifies the activity about the change in its state — the system is creating, stopping, resuming it, or destroying the process it lives in. Inside these callbacks you write what your app should do at that moment.

Streaming video example from the notes: pause the video and close the network connection when the user switches app; reconnect and resume from the same spot when they return.
3 Why needed?

A phone runs many apps but has one screen and limited memory and battery. The user constantly leaves and re-enters apps. Doing the right work at the right time makes your app robust and performant: it does not crash, does not waste resources, and does not lose the user’s work.

4 When needed?

All the time — every time the user opens your app, gets a phone call, presses Home, presses Back, rotates the screen, uses multi-window, or Android kills your app to free memory. In each case you may need to pause, save, release or restore something.

5 What happens without it?

If you ignore the lifecycle, your app may crash on an incoming call, keep using camera/GPS/data in the background, lose the form the user was filling, or lose progress when the screen rotates between portrait and landscape.

You type a long eSewa remark, rotate the phone — and the text is gone. That is a lifecycle bug.
6 How it works?

Android itself decides when the state changes and calls your overridden methods in a fixed order: onCreate() → onStart() → onResume() on the way in, onPause() → onStop() → onDestroy() on the way out, plus onRestart() when coming back from stopped. You never call these yourself; you override them and always call super.onX() first.

07onCreate()

1 What is it?

onCreate() is the first lifecycle callback. The notes say: “You must implement this callback, which fires when the system first creates the activity.” When it runs, the Activity enters the Created state.

Think of it as the opening ceremony of a new shop: the shelves are built once, before any customer walks in.
2 What does it do?

It performs the basic startup logic that should happen only once for the entire life of the activity: calling setContentView() to put the layout on screen, finding views with findViewById(), attaching click listeners, and reading any data passed in (Intent extras or the saved Bundle).

College registration app: onCreate loads activity_register.xml, finds the Name and Roll-no EditTexts and sets up the Submit button listener.
3 Why needed?

The screen must be built before the user can see it. If we built the layout every time the user returned (onResume), we would waste time and might reset what they typed. onCreate gives us one safe place to do one-time setup.

4 When needed?

Called when the activity is launched for the first time, when it is re-created after rotation (a new instance), and when the user navigates back after the app process was killed for memory (see Fig 4-1).

5 What happens without it?

If you don’t override it (or don’t call setContentView), the activity shows a blank screen — nothing to tap. If you forget super.onCreate(b), Android throws a SuperNotCalledException and the app crashes.

6 How it works?

Android creates your Activity object and calls onCreate(Bundle b). You first call super.onCreate(b) so the parent class sets things up, then inflate your XML and wire up views. The Bundle parameter is null on a fresh start. Right after onCreate finishes, Android calls onStart().

08onStart()

1 What is it?

onStart() is called when the activity enters the Started state. The notes: “The onStart() call makes the activity visible to the user, as the app prepares for the activity to enter the foreground and become interactive.”

The shop’s shutter goes up — people outside can now see inside, but the counter isn’t open yet.
2 What does it do?

It makes the activity visible and is where the app initializes code that maintains the UI — for example refreshing a list that may have changed while the user was away, or registering something that updates the screen.

Bus ticket app: onStart refreshes the “seats left” label so the screen shows fresh data whenever it becomes visible.
3 Why needed?

An activity can become visible many times (first launch, and every return from the stopped state through onRestart). onStart is the hook for “I am about to be seen again” work, separate from one-time onCreate work.

4 When needed?

Right after onCreate() on first launch, and after onRestart() when the user navigates back to a stopped activity. It completes very quickly; the activity does not stay in Started — next comes onResume().

5 What happens without it?

If you put “refresh UI” code only in onCreate, a user returning from another app would see stale data (old seat count, old balance) because onCreate does not run again on return.

6 How it works?

Android calls onStart(); you call super.onStart() then do quick UI preparation. Keep it light — heavy work here delays the screen. As soon as it returns, the system calls onResume().

Callback 3 of 6

09onResume()

1 What is it?

onResume() is called when the activity enters the Resumed state and comes to the foreground. The notes: “This is the state in which the app interacts with the user.” This is what we call running.

The shop counter is open — customers can actually buy.
2 What does it do?

It marks the moment the user can touch and type. Here you start or restart things that should run only while the user is actively using the screen: camera preview, animations, sensors, the video player, live location for a ride map.

Pathao map screen: onResume turns on live GPS updates so your rider position moves on the map.
3 Why needed?

Some work only makes sense while the user is looking and interacting. Starting it in onResume (and stopping it in onPause) keeps the app responsive and saves battery.

4 When needed?

After onStart(), and also every time the user returns to a paused activity (dialog closed, call ended). The app stays in this state until something takes focus away: a phone call, navigating to another activity, or the screen turning off.

5 What happens without it?

If you start the camera or GPS only in onCreate and stop it in onPause, then after a phone call ends the camera stays frozen/black — nothing restarts it. Resume is the mirror image of pause.

6 How it works?

Android calls onResume(); you call super.onResume() and (re)start foreground work. The activity is now running. The next callback will be onPause() when focus is lost.

Callback 4 of 6

10onPause()

1 What is it?

onPause() is “the first indication that the user is leaving your activity (though it does not always mean the activity is being destroyed)”. The activity is no longer in the foreground, though it may still be visible (e.g. in multi-window mode). State: Paused.

2 What does it do?

Use it to pause or adjust operations that should not continue (or should continue only in moderation) while paused, and that you expect to resume shortly: pause the video, stop animations, stop GPS updates, release the camera.

Khalti payment screen: a low-battery dialog pops up → onPause stops the 60-second OTP countdown animation.
3 Why needed?

The user’s attention has moved. Continuing heavy work wastes battery and data, and some resources (camera, microphone) must be freed so the other app (e.g. the phone call) can use them.

4 When needed?

The notes give three reasons:

  • Some event interrupts app execution (e.g. a phone call) — the most common case.
  • Android 7.0 (API 24)+ multi-window: only one app has focus, so the system pauses all others.
  • A new semi-transparent activity (such as a dialog) opens; while partially visible but not in focus, it remains paused.
5 What happens without it?

The video keeps playing during the call, the camera stays locked so WhatsApp video call cannot open it, GPS drains battery. In bad cases the app crashes when it tries to use a resource that another app took.

6 How it works?

Android calls onPause(); you call super.onPause() and pause work. Keep it very short — the next screen waits for onPause to finish. If the user comes back, onResume() runs; if the activity becomes fully hidden, onStop() runs.

Callback 5 of 6

11onStop()

1 What is it?

onStop() is called when the activity is no longer visible to the user — it has entered the Stopped state.

The shop has pulled the shutter down; the shop still exists, just nobody can see it.
2 What does it do?

The notes say to use onStop for relatively CPU-intensive shutdown operations: “if you can’t find a more opportune time to save information to a database, you might do so during onStop()”. Also release things not needed while invisible.

College registration app: when you press Home half-way, onStop saves the draft form (name, roll no.) to the local database.
3 Why needed?

onPause must be quick, but onStop has more time because the user is no longer looking. It is the right moment for heavier saving so the user does not lose progress if Android later kills the app.

4 When needed?

When a newly launched activity covers the entire screen, when the user presses Home or switches apps, and when the activity has finished running and is about to be terminated (Back → onPause → onStop → onDestroy).

5 What happens without it?

If you don’t save here, and Android kills the stopped app to free memory (“Apps with higher priority need memory” in Fig 4-1), the user returns to an empty form — all progress lost.

6 How it works?

After onPause, if the activity becomes fully hidden, Android calls onStop(). Call super.onStop() then save/release. From Stopped, three things can happen: user returns → onRestart(); activity finishes → onDestroy(); or the process is killed.

Callback 6 of 6

12onDestroy()

1 What is it?

onDestroy() is “called before the activity is destroyed”. It is the last callback an Activity instance receives.

2 What does it do?

It should release all resources that have not yet been released by earlier callbacks such as onStop() — background threads, open connections, listeners — so nothing leaks after the screen is gone.

3 Why needed?

Once the object is destroyed, any leftover resource is wasted memory (a memory leak) and can slow down or crash the phone over time.

4 When needed?

The notes give two reasons:

  • The activity is finishing — the user completely dismisses it (Back) or finish() is called on it.
  • The system is temporarily destroying it due to a configuration change (device rotation or multi-window mode).
5 What happens without it?

Threads keep running after the screen closes, network sockets stay open, and memory usage keeps growing. On rotation, if you don’t understand that the old object is destroyed, you may hold references to dead views.

6 How it works?

If finishing, onDestroy is the final callback. If caused by a configuration change, the system immediately creates a new activity instance and calls onCreate() on it in the new configuration. So rotation = onPause → onStop → onDestroy → onCreate → onStart → onResume.

The 7th callback

13onRestart()

1 What is it?

onRestart() is the callback on the right side of Figure 4-1. It is called when a stopped activity is about to start again because the “user navigates to the activity”. It appears in the notes’ lifecycle demo code with the log “Activity Restarted”.

2 What does it do?

It lets you run code only for the “coming back” case — not for the first launch. After it, Android continues with onStart() and onResume().

Daraz: you went to WhatsApp and came back — onRestart could check if prices changed while you were away.
3 Why needed?

onStart runs both on first launch and on return. If you need to know “this is a return from stopped”, onRestart is the clear signal.

4 When needed?

Only from the Stopped state: user pressed Home / opened another full-screen app, then comes back via recents or the launcher icon. Never on first launch, never after a dialog (that was only Paused).

5 What happens without it?

Nothing breaks — it is optional. But you might put “return” logic in onStart and accidentally run it on the very first launch as well.

6 How it works?

Stopped → user navigates back → onRestart() → onStart() → onResume(). The object was not destroyed, so your variables and typed text are still there.

19Creating Multiple Activities

“So far we have created and tested only a single activity. Now we are going to create multiple activities and also learn about linking different activities.”

1 What is it?

Multiple activities means an app made of two or more screens, each its own Activity class with its own layout XML. In the notes: FirstActivity (a TextView + a Button) and SecondActivity (a TextView).

Bus ticket app: SearchActivity → SeatSelectActivity → PaymentActivity → TicketActivity.
2 What does it do?

It splits a big app into focused screens, each doing one job. Activities are then linked so the user can move from one to the next (using Intents) and come back (using Back).

3 Why needed?

One screen cannot hold login, product list, cart and payment at the same time on a 6-inch phone. Separate activities keep each screen simple, easier to code, test and reuse.

4 When needed?

As soon as your app needs a new screen with a different purpose: a details page, a form, a result page, a settings page. Every exercise in this unit that says “display in another activity” needs this.

5 What happens without it?

You would cram everything into one layout, hiding/showing views by hand — messy code, confusing UI, and the Back button would just exit the app instead of returning to the previous screen.

6 How it works?

Three steps: (1) create a Java class for each activity that extends Activity and calls setContentView() with its own XML; (2) design each XML layout; (3) declare every activity in AndroidManifest.xml. Then link them with an Intent.

21Activities pile up like a stack of cards

When FirstActivity starts SecondActivity, the new one is placed on top; the old one is stopped underneath (not destroyed). Pressing Back finishes the top one (onPause → onStop → onDestroy) and the one below comes back (onRestart → onStart → onResume). Android calls this pile the back stack.

Manifest · Concept

22Declaring Activities in Manifest

1 What is it?

AndroidManifest.xml is the app’s official registration form that Android reads before running anything. Declaring an activity means adding an <activity android:name=".SecondActivity"/> entry inside <application>. The notes: we now declare both FirstActivity and SecondActivity.

Like your college admission register: if your name isn’t in the register, the exam office won’t let you sit — even if you are standing at the door.
2 What does it do?

It tells Android which activities exist in the package, and — through an <intent-filter> with action.MAIN + category.LAUNCHER — which one is launched first when the user taps the app icon.

3 Why needed?

Android only starts components it knows about, for security and so the launcher knows what to show. The Manifest is that list.

4 When needed?

Every time you add a new Activity class. (Android Studio’s “New → Activity” wizard adds it for you; if you create the Java file by hand, you must add it yourself.)

5 What happens without it?

Calling startActivity() for an undeclared activity crashes with ActivityNotFoundException: “have you declared this activity in your AndroidManifest.xml?”. Without a LAUNCHER intent-filter, the app has no icon to open.

6 How it works?

At install time Android reads the Manifest. When the icon is tapped, it finds the activity with MAIN/LAUNCHER — in the notes that is FirstActivity, “so FirstActivity will be launched first”. Later, when an Intent asks for SecondActivity, Android checks the list and starts it.

23Connecting Activities with Intents

“An intent is an object that a component can use to communicate with the OS.”

1 What is it?

An Intent is a message object — a request you hand to Android saying “please do this for me”. Components that use intents include activities, and also services, broadcast receivers and content providers (you will meet those later).

Like giving a parcel slip to the Nepal Post counter: you don’t carry the parcel to Pokhara yourself — you write the destination and the post office delivers it.
2 What does it do?

Here it tells the ActivityManager (part of Android OS) which activity to start. Intents are multi-purpose communication tools, and the Intent class provides different constructors depending on what you use it for.

3 Why needed?

One activity cannot create and show another screen by itself (you never write new SecondActivity()). Only the OS can create activities, manage their lifecycle and put them on the back stack. So we must ask the OS — with an Intent.

4 When needed?

Whenever you move from one screen to another: Click Me → SecondActivity, Daraz product → cart, “Pay with Khalti” → payment screen. Also whenever you want to carry data to the next screen (extras) or get a result back.

5 What happens without it?

Buttons could not open new screens; your app would be stuck on one activity forever. Writing new SecondActivity() creates a plain Java object with no window and no lifecycle — nothing appears.

6 How it works?

Use the constructor public Intent(Context packageContext, Class<?> cls). The Class object says which activity the ActivityManager should start; the Context tells the ActivityManager which package the Class can be found in. Then call startActivity(i) — the OS reads the intent and launches SecondActivity (Figure 4-3).

25Passing Data Between Activities

“Between activities data can be passed and received by using Intent extras.”

1 What is it?

Extras are “arbitrary data that the calling activity can include with an intent”. Each extra is a key-value pair: a String key (name tag) and a value (number, text, boolean …).

Like writing on the parcel: "name" → "Ram", "address" → "KTM".
2 What does it do?

It carries information from one screen to the next. The OS forwards the intent to the recipient activity, which can then access the extras and retrieve the data.

Daraz: ProductActivity sends "productId" → 1029 to CartActivity so the cart knows what you chose.
3 Why needed?

Each activity is a separate object with its own variables; SecondActivity cannot read FirstActivity’s variables directly. Extras are the official, simple way to hand data across.

4 When needed?

Whenever the next screen needs something from the current one: student id/name/address to a profile screen (notes example), selected seat to a bus-ticket payment screen, the amount to an eSewa confirmation screen.

5 What happens without it?

The next screen opens empty — it doesn’t know which student, product or amount. Developers then misuse global static variables, which break when Android kills and re-creates the app.

6 How it works?

Sender: i.putExtra(key, value) — e.g. public Intent putExtra(String name, boolean value). putExtra comes in many flavors but always has two arguments: first a String key, second a value whose type varies. Receiver: getIntent() then getIntExtra(key, default) / getStringExtra(key). Keys must match exactly (case-sensitive).

Result back · Concept

27Getting Result Back from Child Activity

1 What is it?

So far data went forward (First → Second). Getting a result back means the child activity (SecondActivity) sends data back to the parent activity (FirstActivity) when it closes.

Pathao: Home opens “Choose destination”; you pick “Thamel” and the chosen place comes back to Home.
2 What does it do?

It creates a round trip: parent starts child with a request code, child sets a result (code + intent with extras) and finishes, parent receives it in onActivityResult().

3 Why needed?

Many screens exist only to pick or confirm something — choose a contact, pick a date, complete an eSewa payment — and the parent needs the answer to continue.

4 When needed?

When the parent needs an answer from a child screen. The request code matters when an activity “starts more than one type of child activity and needs to tell who is reporting back” (e.g. code 1 = pick date, code 2 = pick seat).

5 What happens without it?

With plain startActivity(), the child cannot return anything; when it closes, the parent has no idea what the user chose — you would have to re-ask the user.

6 How it works?
  • Parent opens child: public void startActivityForResult(Intent intent, int requestCode) — the request code is a user-defined integer sent to the child and received back by the parent.
  • Child sends back: public final void setResult(int resultCode) or setResult(int resultCode, Intent data), then finish().
  • Parent receives by overriding onActivityResult(...).

29Getting and Setting Data to/from Layout File

1 What is it?

Getting data means reading what the user entered in widgets of the XML layout (EditText, RadioButton, Spinner). Setting data means writing a value into a widget, e.g. txtResult.setText(...). The notes build a Student Form with TextView, EditText, RadioButton, Spinner and Button.

2 What does it do?

It connects the XML design to the Java logic: Java finds each widget by its id, pulls the values out, processes them, and puts the answer back on the screen.

College registration: read Id “111”, Name “Ram Sharma”, Gender “Male”, Program “BCA”, then display them in a TextView (Figure 4-6).
3 Why needed?

XML only draws widgets; it cannot react or calculate. Every real form — eSewa login, Daraz address, bus-ticket passenger details — needs Java code to read inputs and show results.

4 When needed?

Whenever the user types, selects or taps something your code must use — typically inside a button’s onClick() (Submit, Calculate, Pay).

5 What happens without it?

The form looks nice but does nothing: Submit can’t see what was typed, and nothing is shown back to the user.

6 How it works?
  • Give every widget an android:id in XML.
  • In onCreate(): findViewById(R.id.edtId) for each.
  • EditText → getText().toString(); RadioButton → isChecked(); Spinner → getSelectedItem().toString().
  • Show the result with setText() on a TextView.

34Real apps, real lifecycle questions

Start a 60s timer in Class mode, discuss in pairs, then tap a card to reveal a model answer.

🚌

Bus ticket booking: you selected seats A3, A4 and an incoming call arrives. Which callbacks fire, and where should the selected seats be saved?

Call screen is full-screen → onPause → onStop. Save the selection at the latest in onStop (notes: save to database in onStop). On return: onRestart → onStart → onResume.
💳

Khalti: the payment screen is opened from Daraz checkout and must report “success / failed” back. Which technique from this unit?

startActivityForResult(intent, requestCode) from checkout; payment screen calls setResult(code, dataIntent) + finish(); checkout reads it in onActivityResult and checks the requestCode.
🛵

Pathao map uses GPS. The user opens WhatsApp for 10 minutes. What should happen to GPS and why?

Stop GPS updates in onPause/onStop (save battery/resources), restart them in onResume — avoids “consuming valuable system resources when the user is not actively using it”.
🎓

College registration: a student rotates the phone while filling the form. What does Android do to the activity?

Configuration change → onPause, onStop, onDestroy on the old instance, then a new instance: onCreate, onStart, onResume. Unsaved data may be lost unless you save and restore it.
